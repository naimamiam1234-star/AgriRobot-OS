# تعريف المتحكمات ومعرفة الروبوت بحالته — تصميم للمراجعة

التاريخ: 2026-10-19. الحالة: مواصفات مقترحة، لا firmware منفذ أو مختبر على لوحة. توسعة معمارية للمشروع؛ البرامج الحالية والمحاكاة لا تزال كما تصفها STATUS.md.

## ما المقصود بمعرفة الروبوت بحالته؟

نموذج تشغيلي يصف القطع الموجودة، والروابط، وإصدارات البرامج، والقياسات الحديثة، وما يمكن تنفيذه وما لا يمكن تنفيذه، وسبب التوقف. هذه قدرة هندسية على مراقبة الذات وتفسير الحالة، وليست إثباتًا للشعور أو الوعي البشري.

الهدف الذي طلبه المستخدم: ملف داخل كل متحكم يصف منافذه وبرنامجه ووظيفته وما يرتبط به، مع تحليل من المساعد واكتشاف يستند إلى الأدلة. لا يفترض النظام أن ملف التعريف وحده يثبت وجود قطعة أو صحتها.

## مقارنة طرق التنفيذ

| الطريقة | النتيجة | القرار |
|---|---|---|
| تعريف ثابت + فحوص مسموحة + قياسات فعلية | تفسير قابل للتتبع مع حالات مجهولة واضحة | الموصى بها |
| تخمين جميع القطع من GPIO وADC فقط | كثير من الالتباس؛ الجهد نفسه قد ينتج عن قطع مختلفة | غير كافية للتعرف الموثوق |
| ROS كامل داخل كل متحكم | تكامل غني عند توفر ذاكرة ولوحة مدعومة | يدرس لاحقًا؛ لا نفترض ملاءمته لـF103C6 |

نعتمد بروتوكولًا صغيرًا للمتحكمات، ويحوّل مضيف لينكس النتائج لاحقًا إلى رسائل ROS وتشخيصاته. تبقى نماذج اللغة والرؤية على الحاسوب.

## نطاق أول إصدار

- متحكم أول مرشح: STM32F103C6 Blue Pill، ومتحكم ثان مرشح: ESP32 DEVKITC V4.
- بيانات وصف المنافذ والقطع تُولد من ملف المشروع المعتمد، وتضمّن في firmware عند البناء.
- متحكم واحد يرسل بياناته للمضيف، ثم نوسع البروتوكول لعدة متحكمات.
- وضع الفحص يبدأ دون حركة أو ضخ. تعريف المحركات لا يساوي تشغيلها.
- لا نعين أرجلًا فعلية للمحركات أو المضخات حتى نعرف نوع سائق القدرة والتوصيل والجهد.

## ملف التعريف داخل المتحكم

| القسم | محتواه |
|---|---|
| هوية اللوحة | board_id، نوع MCU، رقم العتاد إن توفر، إصدار البروتوكول |
| هوية البرنامج | اسم firmware، نسخته، معرف بناء، بصمة ملفه، ورابط commit المصدر إن توفر |
| المنافذ | اسم الرجل، وظيفتها المهيأة، اتجاهها، نوع الواجهة، وحدودها حسب ملف اللوحة |
| القطع المعلنة | component_id، طراز متوقع، نوع الربط، الدور، الوحدات |
| الروابط | المتحكم ← الواجهة/المنافذ ← القطعة ← وظيفتها في الروبوت |
| القيود | أقصى سرعة/زمن تشغيل وحدود قياس واشتراطات التشغيل |
| فحوص مسموحة | فحص محدد لكل قطعة مع شرط تنفيذه وطريقة تفسيره |
| المراقبة | heartbeat، reset_reason، uptime، أخطاء وبرامج حماية إن كانت مدعومة |

الملف يصف برنامجنا الذي نبنيه. لا يستطيع المتحكم تحويل أي ملف BIN مجهول إلى كود مصدر أو شرح صحيح تلقائيًا. شرح المنطق يستند إلى مصدر متاح ووصف وظائف موثق وبصمة بناء، ولا يعامل تفسير النموذج باعتباره تحليلًا برهانيًا للبرنامج.

## مستويات الدليل

1. declared: القطعة مسجلة في التعريف فقط.
2. observed: شوهدت إشارة أو استجابة؛ النوع لم يؤكد.
3. identified: تطابق معرف مميز وواجهة متوقعة وفق فحص موثق؛ قد يتعرف إلى عائلة لا طراز كامل.
4. verified: اجتازت فحوصًا وظيفية محددة في وقت مسجل؛ ليس ضمانًا دائمًا.
5. inferred: استنتاج غير مؤكد من النموذج، مع سبب ودليل وحدود.
6. unknown/conflict: أدلة ناقصة أو متعارضة؛ التشغيل المرتبط بها غير مفعّل.

كل ملاحظة تتضمن المصدر ووقت الاستلام ومهلة الصلاحية. قراءة قديمة لا تصبح قراءة حالية لمجرد بقاء اللوحة متصلة.

## ما يمكن اكتشافه وما لا يمكن

- USB قد يعرّف الجهاز أو جسر USB-UART؛ تعريف الجسر لا يثبت طراز الحساس خلفه.
- I2C: الاستجابة عند عنوان تعني وجود استجابة لذلك العنوان؛ الطراز يحتاج معرفات وفحوصًا مناسبة، وبعض القطع تشترك بالعناوين.
- ADC/GPIO: يقيس مستوى أو جهدًا ضمن شروط الدارة؛ لا يميز تلقائيًا بين كل حساس ومقاومة أو خط غير موصول.
- المحرك: ملف تعريف سائق القدرة والإنكودر والتيار والاختبارات ضروري؛ لا يبدأ دورانًا لتخمين القطعة.
- SPI/UART: الربط والطرفيات والجهد والسرعة محددة مسبقًا؛ لا نرسل أوامر عشوائية إلى قطع مجهولة.
- لا ننفذ فحصًا شاملاً يبدّل اتجاه جميع GPIO؛ قد تكون أرجل إقلاع أو مخارج لسائق قدرة. فحوص التعرف محصورة بملف اللوحة والتجميعة المسموحة.

## قناة الاتصال المقترحة

رسائل قصيرة متسلسلة بنص JSON محدود، عبر UART أو USB المدعوم بالبرنامج. الحد المقترح 768 بايت للإطار، وترسل قوائم المنافذ والقطع على عدة إطارات لتناسب المتحكم الصغير. لا يخصص buffer بحجم جميع البيانات دفعة واحدة.

الأحداث الأساسية: hello، manifest_part، component_status، telemetry، fault، heartbeat. الطلبات: read_manifest، read_status، run_allowed_probe، stop. أوامر الحركة والضخ لها طبقة منفصلة ولا تتاح للمساعد اللغوي مباشرة.

كل إطار يحمل protocol_version وsession_id وsequence وmessage_type وpayload وCRC. CRC لكشف تلف النقل، وليس توقيعًا يثبت هوية متحكم قد يكذب أو يكون غير موثوق. طول الرسائل والحقول والقيم والتكرار تتحقق قبل التخزين.

عند فقد heartbeat تصبح قياسات اللوحة غير متاحة ويطلب التوقف من طبقة التحكم. عند إعادة الاتصال يبدأ تحقق جديد؛ لا يستأنف أمر سابق تلقائيًا. زمن المهلة يعتمد على اختبار الحركة الفعلي، وليس على زمن رد النموذج اللغوي.

## طبقات البرمجيات المطلوبة بعد اعتماد التصميم

| الوحدة | مسؤوليتها |
|---|---|
| firmware/common | ترميز الإطارات وحدود الذاكرة والرسائل والأخطاء |
| firmware/stm32f103c6 | تنفيذ خصائص اللوحة المدعومة وتضمين تعريفها |
| firmware/esp32 | تنفيذ خصائص ESP32 المدعومة وتضمين تعريفها |
| config/boards | ملفات قدرات اللوحات، ومراجع الأرجل الموثقة |
| config/assemblies | التوصيلات المعتمدة للروبوت الفعلي؛ مستقلة عن قدرات اللوحة العامة |
| app/device_registry | تسجيل الهوية والإصدارات وحالة الوثوق والوقت |
| app/evidence | مستويات الدليل والتعارضات والتقادم |
| app/robot_context | صورة موحدة للمكونات والروابط والحالة والحدود |
| app/assistant_context | قراءة هذه الصورة لصياغة إجابة مع أسباب ومصادر |
| app/motion | تحقق محدد القواعد، وأوامر محدودة مع deadman وwatchdog مستقلين |

تعريف الثقة لا يقبل من كلام المتحكم نفسه فقط. ملف التجميعة في المضيف يحدد المتوقع؛ الاختلاف يسجل كتعارض يحتاج مراجعة.

## مثال لسلوك المساعد

عند السؤال عن حساس الرطوبة، يذكر أن التعريف يتوقع حساسًا تناظريًا على المدخل المخصص، وأن آخر قراءة وصلت منذ زمن معين، وأن هوية طراز القطعة لم تؤكد إلكترونيًا. عند السؤال لماذا توقف، يربط السبب بحدث مسجل مثل فقد اتصال لوحة الحركة. لا يدعي رؤية سلك مفصول إذا كان دليله الوحيد فقد القراءة.

إذا طلب المستخدم تحريك الروبوت، تمر النية إلى طلب مخطط ومحدود؛ يرفض التحكم التنفيذ عند جهل سائق القدرة أو عدم المعايرة أو غياب مساحة آمنة أو توقف الطوارئ. التوليد اللغوي لا يعيد برمجة المتحكم ولا يغير التوصيلات تلقائيًا.

## الصور والذكاء الاصطناعي

توسعة الصور تتم كمجموعات معروفة النطاق والترخيص، لا مجموعة تدّعي جميع الأنواع عالميًا. PlantDoc مرجع أوراق مصنفة؛ لا يحوّل مباشرة إلى نموذج اكتشاف حشرات بمربعات تحديد. تبقى فئات التدريب والاختبار الأصلية منفصلة، وتجمع بيانات محلية للمحصول.

Qwen للمحادثة وتفسير السياق، Whisper لفهم الصوت، ومحرك صوت مرخص، وكاشف بصري مدرب للمهمة. وصف صورة توليدي اختياري. تنزيل الأوزان لا يثبت نجاح الاستدلال أو دقة زراعية. قبل إدراج أي نموذج في ISO نحتاج ملف ترخيص، revision وhash، اختبار استدلال فعلي، وقياس RAM والزمن على CPU مناسب.

## إضافات مرتبطة مباشرة بهذا التصميم

1. اكتشاف اختلاف firmware بين لوحتين ومقارنته بإصدار التجميعة.
2. كشف قطعة معلنة لا تستجيب مع بيان حدود فحصها.
3. تتبع سبب القرار إلى قراءة ووقت وفحص، لا إلى إجابة لغوية فقط.
4. ملف صيانة بعد استبدال قطعة، مع معايرتها وتاريخ الاستبدال.
5. تسجيل reset/brownout عند دعم اللوحة وشرح أثره المحتمل دون تأكيد سبب كهربائي غير مقاس.
6. وضع فحص كهربائي ساكن لا يشغل محركات أو مضخات.
7. مراقبة تعارض استعمال الرجل الواحدة في ملف التجميعة قبل البناء.
8. مقارنة القياس المتوقع بالفعل بعد تنفيذ أمر معاير، مثل التدفق أو الإنكودر.

هذه أنماط هندسية للتحكم والتشخيص؛ لا ندعي أنها اختراعات جديدة عالميًا.

## اختبارات القبول المطلوبة

- رفض إطار طويل أو CRC خاطئ أو نسخة بروتوكول غير مدعومة.
- منع رفع observed إلى identified دون فحص تعريف موثق.
- منع اختلاط session قديمة بجديدة بعد إعادة التشغيل.
- فقد الاتصال يجعل الحالة stale ولا يولد قراءات بديلة.
- حساس بعنوان مشترك يبقى unknown عند غياب معرف مميز.
- ملف منافذ متعارض يرفض قبل تشغيل المخارج.
- التشخيص لا يكتب إلى رجل مجهولة ولا يفعّل الحركة.
- اختبار بناء firmware لكل لوحة، وقياس حجم Flash وRAM، ثم اختبار منصة فعلية دون أحمال خطرة.
- اختبار أن المساعد يقول «غير معروف» عند غياب دليل، ولا يحول ملف التعريف إلى دليل وجود فعلي.
